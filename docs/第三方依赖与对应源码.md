# 第三方依赖、许可及对应源码

词链 v1.2.0 的应用代码以 **GPL-3.0-or-later** 发布，完整文本见根目录 `LICENSE`。离线运行时静态链接了 eSpeak NG，因此软件整体采用兼容的 GPL 许可。词库、例句和下载的模型权重分别保留自己的许可及署名，软件许可不替代数据许可。

安装包包含 `assets/licenses/dependencies/` 的完整运行时许可与通知。根目录 `NOTICE` 汇总软件依赖；原词库/例句的通知继续保留在 `assets/NOTICE.txt`。模型权重不随安装包分发，模型目录列出来源、许可与校验信息。

## 本次发布所用二进制

采用官方 [sherpa-onnx v1.13.8](https://github.com/k2-fsa/sherpa-onnx/releases/tag/v1.13.8) 的 CPU、静态 ONNX Runtime Android AAR：

- 下载：<https://github.com/k2-fsa/sherpa-onnx/releases/download/v1.13.8/sherpa-onnx-static-link-onnxruntime-1.13.8.aar>
- SHA-256：`b22c3fc1b6a45666d28892bb2f7694beeb77a8362d7ebd77c1a5431ec9435471`。
- 提取 `classes.jar` 为 `app/libs/sherpa-onnx-android-1.13.8.jar`，只提取 `arm64-v8a` 与 `armeabi-v7a` 的 `libsherpa-onnx-jni.so`。
- 原生库的字节保持官方原样；以 gzip level 9、空文件名、mtime=0 封装入 `app/native/`，便于公开仓库传输。Gradle 用 JDK 的 GZIP/SHA-256 自动还原；直接 SDK 脚本用 Python 标准库还原。
- 所有 JAR、压缩文件与还原后 SO 的精确字节数和 SHA-256 见 `dependencies.lock.json`。`python3 scripts/verify_dependencies.py` 验证全部文件。构建无需下载模型权重。

源码和 CI 不包含本次更新用的签名私钥。使用自有密钥可编译安装修改版；不能用其他证书覆盖已安装的发布版。APK 签名证书与原生代码的构建独立。

## 从源码重新构建原生运行时

原始官方流程见 [v1.13.8 的 android-static.yaml](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/.github/workflows/android-static.yaml)。本次两个 ELF 的 Android note 标识 NDK r29 build 14206865、API 21；应用最低系统仍为 API 26（Android 8.0）。使用 Ubuntu、CMake、make、JDK、Android SDK 和该 NDK，可采用原始控制脚本：

```bash
git clone --branch v1.13.8 --depth 1 https://github.com/k2-fsa/sherpa-onnx.git
cd sherpa-onnx
export ANDROID_NDK=/absolute/path/to/android-ndk-r29
export BUILD_SHARED_LIBS=OFF
./build-android-arm64-v8a.sh
./build-android-armv7-eabi.sh
```

两个脚本默认开启 TTS/JNI，关闭 Python、测试、PortAudio 等；`BUILD_SHARED_LIBS=OFF` 选择静态 ONNX Runtime。输出分别在 `build-android-arm64-v8a-static/install/lib/` 和 `build-android-armv7-eabi-static/install/lib/`。eSpeak NG 和 piper-phonemize 的固定源码由随版本的 CMake FetchContent 获取。保留这些源文件即可修改并重新链接 eSpeak，而不需要原发布私钥。

若需重建 Java/Kotlin 桥接 JAR，将输出的 JNI 文件复制到官方 `android/SherpaOnnxAar/sherpa_onnx/src/main/jniLibs/<ABI>/`，然后在 `android/SherpaOnnxAar/` 运行 `./gradlew :sherpa_onnx:assembleRelease`。从新 AAR 提取 `classes.jar` 和 JNI 即可。修改依赖后应重新生成压缩文件和 `dependencies.lock.json` 校验值，再运行应用构建。官方工具链和构建机器的差异可能导致二进制哈希不同；上述流程是对应源码重建方法，不宣称复建后逐字节相同。

## 本次兼容性验证边界

两个 ARM ELF 的 LOAD 段对齐均为 16KB；ARM64 的 RELRO 对齐检查通过。universal 安装包存储未压缩 JNI，并以 `zipalign -P 16` 对齐；单 ABI 下载包压缩 JNI，设置 `extractNativeLibs=true` 让系统安装时解压。两种打包路径均做签名和 ZIP 校验。未在真实 16KB Android 设备上运行，不宣称全机型验证通过。

已用官方同版本 Linux JNI 和真实 Kitten/Piper/Kokoro 模型生成有限、非零音频，结果见 `tests/native_model_validation.json` 与构建报告。Linux 检查不能替代手机端 JNI、AudioTrack 或性能测试。
